## Video 2: Overview of Model Persistence and Serving

The process to create a machine learning model typically involves training and validating the model using data. The process begins with the collection and preprocessing of a high-quality training dataset. The data preprocessing step involves important tasks such as data cleaning, data transformation and data reduction. The pre-processed dataset is then used to create features through a feature engineering process. While creating features, it is important to consider model complexity, balancing a trade-off between bias and variance. The dataset consisting of the features is then used to create several machine learning models using different combinations of the features, algorithms and hyperparameters. From here on the model are evaluated using various performance metrices to identify the best model.

As part of the model development process, it is also a good practice to validate the model by splitting the dataset into training partition and testing partition. This split validation process helps to assess whether the model suffers from overfitting problem and thus ensuring its generalisability to new unseen data.

The output of this lengthy and deliberate model development process is final version of the best model, but the process of implementing a machine learning model does not stop here. In fact, the end of the model development process marks the start of another bigger process of model productionisation. The model productionisation process itself can be further divided into three steps as shown in this infographic. As you would have observed, training a machine learning model or model development is just one step in the bigger four step machine learning project lifecycle. We typically term this bigger lifecycle, the machine learning operations, or MLOps process.

As part of the model productionisation process, there are two important tasks that need to be performed. The first task is model persistence, and the second task is model serving. Model persistence refers to the process of saving a trained machine learning model so that it can be reused later without retraining from scratch. This is particularly useful when deploying models in production environments, sharing models with others, or resuming work after an interruption. There are several advantages associated with model persistence. First, model persistence, is more efficient. It saves time and computational resources by avoiding retraining each time the model needs to be used. Second, model persistence affords reproducibility and ensures that the same model can be used consistently across different sessions and applications. Third, model persistence is fundamental to model deployment. Which allows model to be integrated into real-world applications, application programming interfaces, or APIs or other software. Model persistence support version control, which helps in tracking changes and maintaining different versions of a model.

There are various methods for model persistence, depending on the nature of the machine learning model. These methods would be discussed in detail in the subsequent videos.

Model serving refers to the process of deploying a trained model into a production environment where it can receive input data and generate predictions in real-time or batch modes. It is the bridge between model training and real-world application, ensuring that users or software systems can interact with the model efficiently. There are several aspects involved in model serving. First, deployment involves hosting the model on a server or cloud platform so it can be accessed via APIs, web services, or batch processing pipelines. Second, scalability ensures the model can handle varying loads, including traffic spikes by leveraging distributed computing architecture. Third latency and performance focus on optimising inference time to provide real-time or near real-time predictions when required. Fourth, versioning and monitoring entail. keeping track of different model versions and monitoring performance for accuracy drift, latency, and failures. Finally, security and access control, including protecting the model from unauthorised access or adversarial attacks, and ensuring compliance with data privacy regulations. There are several frameworks and architecture for model serving that can be used in real-world context. We will discuss them in the subsequent videos.

Whereas scikit-learn focuses on conventional machine learning models that do not involve deep learning. Tensorflow/Keras focuses on deep learning models. Keras models are thus much more complex. Thus, model persistence in Keras is all the more important. In fact, model persistence in Keras has some added advantages beyond reusing a loaded model for inference. A loaded deep learning model can also be used for fine-tuning and further training or retraining. Keras provides multiple ways to save and load models, including saving the entire model, saving weights only, and saving model architecture separately. We will broadly review each of these methods.

Let's begin with saving the entire model, which is typically the recommended method. This method includes the architecture of the models, the weights and training configuration. It ensures a seamless reloading of the model without requiring additional setup. The code fragments for saving and loading an entire Keras models are generally similar to those for a scikit-learn model. The second method involves the saving of the weights only. This method is useful when you want to reinitialise a model with a new architecture but retain the previously trained weights. Let's look at some scenarios when this method might be useful. A common scenario is to modify the architecture of a deep learning model by adding new layers for transfer learning. More specifically, we might add new classification layers to a pretrained model while keeping the feature extraction layers intact. Sometimes, we might want to change the input shape such as extending a 28x28 input image model to handle 32x32 images while keeping the preceding layers similar. Other times we might modify the activation functions, or layers properties such as replacing ReLU with LeakyReLU without having to be retrain from scratch. As you can see, the second method of saving the weights only can be very useful. The code fragments to save a model's weights is generally straightforward. But a code fragment for loading a model's weights is more complicated because of the need to recreate the model first. Recreating a Keras model involve defining the architecture and compiling the model.

The third method entails saving the model architectural separately. This approach can be useful when you want to recreate the model structure without storing the large weight files. Let's explore some scenarios that might benefit from this method. Sometimes you might want to deploy a model without a training weight so that you can train the model with different user data. You might also want to share your model for collaborative research and open-source sharing without the weights. This is especially useful if the weights are trained on proprietary or sensitive data. Large organisations might also find it useful to standardise their model architecture across different machine learning engineering teams. Again, for such a scenario, the standard architecture is distributed without the weights, so that teams can train on their own datasets.

When performing model persistence in Keras, you might find the use of checkpoints to be useful for saving model progress. Saving checkpoints during training helps to resume the training process if it gets interrupted for whatever reasons. There are some best practices that you might want to keep in mind when persisting a Keras model. Whenever possible, it is good to use the model's .save() method to ensure that the model architecture, weight and optimiser state are saved completely. ## Video 9: Serving a Model Using MLflow

Thus far, we have focused on serving machine learning models via API endpoints created using RESTful web services. These API endpoints can be consumed in the frontend and backend of software systems to integrate the predictions made by machine learning models to automate business processes and decision-making. Besides using API endpoints to serve machine learning models, it is also possible to use platforms such as ML Flow to manage the entire machine learning lifecycle. More specifically, MLflow is an open-source platform designed to handle machine learning, experimentation, reproducibility, deployment, and model management. It helps AI/ML engineers to track their experiments, package models and deploy them in a scalable way.

MLflow consists of four primary components. MLflow Tracking logs and tracks experiment, parameters, metrics and artifacts. MLflow Projects standardises ML codes to ensure reproducibility. MLflow Models, facilitate model packaging, versioning, and deployment. MLflow Registry provides modern version control annotations and lifecycle management.

First, let's examine model logging and registration. Before deployment, MLflow helps log and register trained models.
